# ReaderRSS — персональный новостной агрегатор с LLM-суммаризацией (описание на back и на front-части)

Сервер собирает RSS-ленты мировых СМИ (в основном на английском, плюс немецкий и русский), группирует статьи в сюжеты, суммирует их
через LLM на русском языке и отдаёт через REST API. Android-приложение показывает
ленту сюжетов с фильтрами, офлайн-кэшем и админ-разделом для управления сервером
с телефона.

Ключевой принцип: **сервер делает дорогую работу один раз, клиент читает дёшево
и работает офлайн.**

Актуально на: 2026-11-25. Почему сделано именно так — в [`DECISIONS.md`](DECISIONS.md).

## Архитектура

```
RSS-ленты ──> pipeline.py ──> PostgreSQL ──> api.py (FastAPI) ──> Android-приложение
                  │                                                    │
                  └── OpenRouter (LLM)                           Room-кэш + DataStore
```

| Слой | Технологии |
|---|---|
| Хостинг | VPS, Docker Compose, каталог `/opt/reasderrss` |
| Домен / TLS | `readerrss.duckdns.org` (DuckDNS), HTTPS через Caddy |
| БД | PostgreSQL в контейнере, том `pgdata` |
| API | FastAPI, живая схема на `/docs` |
| Пайплайн | Python, запуск по systemd-таймеру (тик раз в 20 мин, прогон раз в 6 ч) |
| Группировка | эмбеддинги `paraphrase-multilingual-MiniLM-L12-v2` (многоязычные) + DBSCAN |
| LLM | OpenRouter, модель `qwen/qwen3.8-27b` (reasoning-модель) |
| Клиент | Android, Kotlin, Jetpack Compose |

### Модули

|---|---|

| `app/pipeline.py` | прогон: сбор RSS → группировка → LLM → сохранение → очистка |

### Таблицы

| Таблица | Что хранит |
|---|---|
| `articles` | статьи из RSS: источник, заголовок, описание, ссылка, `published_at`; `dedup_key` не даёт загрузить статью дважды; `is_sport` / `sport_words` — только статистика |
| `stories` | сюжеты: заголовок, текст и факты на русском, `category`, `accepted` (попал ли в ленту), `sources`, `source_count`, `rejection_reason` |

| `runs` | журнал прогонов: время, `status` (`running` / `success` / `failed`), `stats` (accepted, rejected, skipped_known, errors) |
| `settings` | параметры пайплайна и флаг `run_requested` (ключ → JSON-значение) |

| POST | `/api/v1/admin/runs` | запрос внепланового прогона (флаг `run_requested`) |

### Пайплайн (`app/pipeline.py`)

1. **Сбор.** Загрузка включённых лент из `feeds`; в `articles` попадают статьи,
   опубликованные в пределах `lookback_hours` (дубли отсекает `dedup_key`).
2. **Выборка.** До `MAX_ARTICLES` (2500) самых свежих статей за окно `lookback_hours`.
3. **Группировка.** Эмбеддинги заголовка и описания, DBSCAN по косинусной близости
   (порог `SIMILARITY_THRESHOLD` = 0.60). Дальше идут только группы минимум из
   `min_sources` разных источников.
4. **Проверка «известности».** Группа пропускается без LLM, если **≥ 70 % её статей
   уже входят в какой-либо сохранённый сюжет** (`story_exists`).
5. **LLM.** Модель проверяет, что статьи про одно событие, пишет заголовок, текст и
   факты строго на русском и выбирает категорию из `app/categories.py`. Принимаются
   все категории, кроме `other` (погода, разные события в одной группе).
   Для отклонённых модель пишет короткую причину (`reason`) — она сохраняется в
   `rejection_reason` как «Разные события: …» или «Категория other: …».
6. **Сохранение** сюжета (принятого или отклонённого) и связей со статьями.
7. **Статус прогона.** `success`, если обработана хотя бы одна группа или ошибок не было;
   `failed`, если **все** группы упали с ошибкой или модель недоступна
   (`ModelUnavailableError`).
8. **Очистка** (только после успешного прогона): удаляются сюжеты, статьи и записи
   `runs` старше `retention_days`.

**Расписание.** `news-worker.timer` → `news-worker.service` каждые 20 минут. Прогон
выполняется, если с последнего **успешного** прогона прошло `pipeline_interval_hours`
или выставлен флаг `run_requested` (кнопка в админке). После неудачного прогона
следующая попытка — не раньше чем через `FAILED_RETRY_MINUTES` (60 мин), чтобы при
стабильной ошибке не тратить кредиты на каждом тике.

**Защита от сбоев LLM** (`app/llm.py`):
- `max_tokens` (`LLM_MAX_TOKENS`) — потолок ответа; без него OpenRouter резервирует
  весь контекст модели и отвечает 402 при небольшом балансе;
- `reasoning.max_tokens` (`LLM_REASONING_MAX_TOKENS`) — потолок «размышлений»
  reasoning-модели, иначе она иногда думает до упора и не успевает ответить;
- `provider.ignore` (`LLM_IGNORE_PROVIDERS`) + `require_parameters` — провайдеры,
  которые игнорируют JSON-режим, исключены;
- если ответ всё же обрезан, но начинается с целого JSON — он используется;
- если JSON спасти нельзя — один повтор (`TRUNCATED_RETRIES`) в обход провайдера,
  давшего обрезанный ответ;
- при обрезке в лог пишется диагностика `[TRUNCATED]`: провайдер, токены ответа и
  размышлений, начало и хвост текста.

### Конфигурация

Файл `.env` (секреты и инфраструктура; читается при каждом запуске воркера,
поэтому после правки пересборка не нужна):

| Переменная | Значение | Назначение |
|---|---|---|
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` | `news`, `news`, … | контейнер PostgreSQL |
| `DATABASE_URL` | `postgresql://news:…@postgres:5432/news` | подключение пайплайна и API |
| `OPENROUTER_API_KEY` | … | ключ OpenRouter |
| `LLM_MODEL` | `qwen/qwen3.8-27b` | модель (тот же дефолт в коде, `DEFAULT_MODEL` в `app/llm.py`) |
| `ADMIN_TOKEN` | … | Bearer-токен админского API |
| `LLM_MAX_TOKENS` | `8000` на проде (дефолт 4000) | потолок ответа модели |
| `LLM_REASONING_MAX_TOKENS` | дефолт 2000 | потолок размышлений; `0` — выключить |
| `LLM_IGNORE_PROVIDERS` | дефолт `ModelRun` | исключённые провайдеры, через запятую |

Параметры пайплайна хранятся **в таблице `settings`** (источник правды);
дефолты заданы в `DEFAULT_SETTINGS` в `app/db.py`. Ключ появляется в таблице
только после первой записи через PUT или SQL. Переменные `.env` на эти параметры
не влияют и не перезаписывают их при рестарте контейнеров.

Текущие значения:

| Ключ | Значение | Примечание |
|---|---|---|
| `pipeline_interval_hours` | 6 | было 2 |
| `lookback_hours` | 36 | было 48 |
| `min_sources` | 4 | задано из админки; дефолт в коде тоже 4 (было 2) |
| `retention_days` | 20 | дефолт, меняется в админке («Хранить данные, дн»); меньше 3 не принимается |

### Стоимость LLM

`qwen/qwen3.8-27b` на OpenRouter: вход $0.035, выход $1.50 за 1 млн токенов —
**$0.002–0.005 за группу** (почти всё — ответ). 4 прогона в сутки по 20–25 групп
из 4+ источников, из них больше половины «известные» и идут без LLM.

До 2026-11-19 воркер работал на старом образе и ходил в LLM каждые 20 минут
(~72 прогона в сутки) — отсюда прежний расход. Контроль — страница Activity в
OpenRouter и `skipped_known` в журнале запусков.

Ограничение региона оплаты: модели OpenAI, Anthropic и Google недоступны,
остальные работают. В кабинете OpenRouter автопополнение выключено, на ключе
установлен лимит.

### Экраны

| Экран | Поведение |
|---|---|
| Лента | чипы категорий из реальных данных; карточки (категория, число источников, заголовок, 3 строки summary, источники, давность); сортировка «день ↓, источники ↓, id ↓»; прокрутка наверх при смене чипа; плашка «Сервер обновлял новости N ч назад», если успешного прогона не было > 12 ч; нижняя панель «обновлено N мин · ЧЧ:ММ» (учитывает и фоновый синк, переживает перезапуск), кнопки обновления и настроек; автосинк при старте; при ошибке сети — снэкбар, лента из кэша остаётся |

### Проектные решения

- Хранятся **скрытые** категории и источники, а не выбранные: всё новое на
  сервере видно пользователю по умолчанию.
- Фильтры применяются в памяти к потоку из Room (`combine` в `FeedViewModel`),
  а не в SQL — проще комбинировать условия, при сотнях сюжетов это мгновенно.
- Скрытый источник убирает сюжет только если он был у сюжета единственным.
- Сетевые ошибки переводятся в человеческие сообщения (`util/userMessage`);
  технический стектрейс уходит только в Logcat.
- Детали сюжета (список статей) не кэшируются — экран сюжета требует сеть.
- Сюжеты старше `retention_days` (с сервера, `/meta`) удаляются из Room при каждом синке:
  клиент тянет только новые по `since_id` и сам не узнал бы об удалении на сервере.
- Адрес сервера — `BuildConfig.BASE_URL` из Gradle.
- Фоновый синк — WorkManager, раз в выбранный интервал при наличии сети. Ночью Android
  (Doze) откладывает фоновые задачи на часы — это поведение системы, не баг; на Samsung
  дополнительно нужно исключить приложение из «спящих».

## Быстрый старт

### Сервер

```bash
cd /opt/reasderrss
cp .env.example .env            # заполнить DATABASE_URL, OPENROUTER_API_KEY, LLM_MODEL, ADMIN_TOKEN
docker compose up -d --build && docker compose build worker   # воркер в профиле worker: up его не пересобирает
docker compose run --rm worker  # ручной прогон пайплайна
systemctl enable --now news-worker.timer
```

Проверка: `https://readerrss.duckdns.org/health`, `https://readerrss.duckdns.org/docs`.

### Приложение

1. Открыть проект в Android Studio, дождаться Gradle sync.
2. Build Variants → `adminDebug`.
3. Адрес сервера — `buildConfigField("String", "BASE_URL", …)` в `app/build.gradle.kts` (по умолчанию `https://readerrss.duckdns.org/`).
4. Запустить на устройстве; в настройках → «Администрирование сервера» → ввести `ADMIN_TOKEN`.

**Release-сборка с подписью.**

1. Один раз создать ключ: Build → Generate Signed App Bundle / APK → APK → Create new…
   Файл `.jks` положить, например, в `keys/` в корне проекта. Ключ и пароли хранить отдельно
   (менеджер паролей + резервная копия файла): обновления подписываются **тем же** ключом,
   иначе телефон не поставит их поверх старой версии.
2. Скопировать `keystore.properties.example` в `keystore.properties` и заполнить путь,
   пароли и alias. `keystore.properties`, `*.jks`, `*.keystore` — в `.gitignore`.
3. Build Variants → `publicRelease` (или `adminRelease`) → Build → Build APK(s).
   APK — в `app/build/outputs/apk/<flavor>/release/`. Терминал: `.\gradlew assemblePublicRelease`.

Без `keystore.properties` release собирается неподписанным (`app/build.gradle.kts`,
`signingConfigs`), debug-сборки от этого не зависят. Release сжимается R8
(`isMinifyEnabled`); правила — `app/proguard-rules.pro`, остальное приносят библиотеки.
Первую release-сборку проверить на устройстве целиком: R8 может сломать то, что работает
в debug (рефлексия Retrofit и сериализации).

### Тесты (сервер)

```bash
cd ~/reasderrss && scripts/run_tests.sh                  # все тесты (~10 с)
scripts/run_tests.sh tests/test_api.py -v                # один файл
scripts/run_tests.sh -k retention                        # по имени
```

**Как устроено.** Одноразовая инфраструктура: временная docker-сеть и PostgreSQL
(данные в памяти), pytest в контейнере из образа `reasderrss-test`
(`Dockerfile.test` = образ воркера + pytest из `requirements-dev.txt`; собирается из
кэша, сам пересобирается после выкатки воркера). Код монтируется только для чтения из
папки, где запущен скрипт. После прогона всё удаляется; прод-контейнеры, том `pgdata`,
`.env` и таймер не затрагиваются. `tests/conftest.py` отказывается работать, если база
называется не `test`.

**Без сети и LLM.** `httpx.post` (OpenRouter), сбор RSS и модель эмбеддингов
подменяются заглушками — тесты бесплатные и дают одинаковый результат.

| Файл | Что покрывает |
|---|---|
| `tests/test_smoke.py` | импорт модулей, схема БД |
| `tests/test_llm.py` | параметры запроса (лимиты, reasoning, JSON-режим, исключение провайдеров), разбор ответа, обрезанные ответы, спасение JSON и повтор без провайдера, HTTP 404/402/429, ошибка сети |
| `tests/test_api.py` | `/meta`, `/stories` (фильтры, `since_id`, пагинация), детали сюжета, доступ к админке, `settings` и проверка `retention_days`, ленты, прогоны |
| `tests/test_pipeline.py` | расписание и повтор после неудачи, очистка, порог «известности», решение по ответу LLM и причина отклонения, прогон `main()` целиком (`success` / `failed`) |
| `tests/factories.py` | заполнение тестовой базы; время задаётся явно («5 часов назад») |

**Правило.** Перед коммитом кода сервера и перед выкаткой — `scripts/run_tests.sh`.
Исправленная ошибка — тест, который падает на старом коде. Новые тесты проверяются
«мутациями»: на копии кода ломается нужное место — тест обязан упасть.

**Ограничение.** Зависимости берутся из образа воркера: новую библиотеку в
`requirements.txt` сначала нужно выкатить, иначе тесты её не увидят.

## Эксплуатация и диагностика

Параметры пайплайна в БД:

```bash
docker compose exec postgres psql -U news -d news -c "SELECT key, value, updated_at FROM settings;"
```

Последние прогоны:

```bash
docker compose exec postgres psql -U news -d news -c "SELECT id, started_at, finished_at, status FROM runs ORDER BY id DESC LIMIT 5;"
```

Таймер и логи воркера:

```bash
systemctl status news-worker.timer

```

Изменение параметров без редеплоя (с сервера, bash):

```bash
curl -X PUT -H "Authorization: Bearer $ADMIN_TOKEN" -H "Content-Type: application/json" \
  -d '{"pipeline_interval_hours": 6, "lookback_hours": 36}' \
  https://readerrss.duckdns.org/api/v1/admin/settings
```

`curl.exe` с экранированными двойными кавычками, Swagger UI на `/docs` или админ-раздел

означает, что воркер не запускался — проверить таймер. Кэш приложения маскирует такой
отказ: лента выглядит живой.

## Ретроспектива

### Что сработало

- Разделение «сервер думает, клиент читает»: клиент почти не генерирует трафика
  (инкремент по `since_id`), стартует мгновенно, работает офлайн.
- Параметры пайплайна в БД + админ-API: обе «ручки экономии» крутились без редеплоя —
  сначала curl'ом, затем с телефона.
- Реактивная цепочка Room/DataStore → `combine` → UI: фильтры, синк и настройки
  сходятся в одном `uiState`, целый класс багов рассинхронизации не возник.
- Flavors вместо «скрытого раздела по паролю»: публичная сборка физически не содержит
  админского входа.

### Чему научились

- Большинство ошибок сборки были про **размещение файлов**, а не про код: файлы в
  `build/generated`, пакет в корне `java`, функция за пределами `object`, заготовка
  `annotation class` над вставленным интерфейсом. Правило: создавать файлы только
  кликом по целевому пакету, тип **File**, сверять строку `package` с путём.
- Версии инструментов в студии всегда новее любых внешних инструкций — при конфликте
  побеждают версии студии (подтвердилось на AGP, Gradle, пакете конвертера Retrofit).
- Экономия на LLM должна подтверждаться метрикой (`skipped_known`, Activity в кабинете),
  а не расчётом: реальный расход оказался в разы выше прогноза из-за неработающей
  дедупликации.
- Кэш маскирует серверные отказы — нужен явный сигнал устаревания данных в интерфейсе.
- Windows-терминал ломает кавычки в JSON — админские операции удобнее делать через
  Swagger UI, по SSH или из приложения.
- Код в репозитории и код в работающем контейнере — не одно и то же: воркер полтора
  месяца работал на образе от 4 октября, потому что профильный сервис не пересобирался.
  Выкатка — с `docker compose build worker`.
- Статус `success` у прогона, где все группы упали, три недели скрывал, что сюжеты не
  создаются. Статус должен отражать результат, а не факт завершения.
- Диагностику стоит логировать сразу: «обрезанный ответ» оказался двумя разными
  проблемами (бесконечные размышления и провайдер, игнорирующий JSON-режим).

**Итог:** продуктовое ядро готово от RSS до экрана телефона. Оставшееся — верификация
и полировка, а не недостроенные части.
