# Журнал решений

Почему в проекте сделано именно так. Новые записи — сверху. Формат: дата, проблема,
решение, почему (и что отвергли). Подробности — в указанных коммитах.

Репозитории: `reasderrss` — сервер, `newsreader` — Android-клиент.

---

## 2026-11-23 — Тесты сервера: pytest на одноразовом PostgreSQL, без LLM

**Проблема.** Тестов не было: падение `/meta` (22.11) дошло до прода, логика
расписания и очистки, от которой зависят деньги и данные, проверялась только логами.
**Решение.** 89 тестов pytest (`tests/`), запуск `scripts/run_tests.sh`: временные сеть и
PostgreSQL в `tmpfs`, тесты в одноразовом контейнере из образа `reasderrss-test`
(образ воркера + pytest), код монтируется только для чтения. OpenRouter, сбор RSS и
модель эмбеддингов подменяются.
**Почему так.**
- Образ воркера как основа — тесты идут на тех же библиотеках, что и прод;
  `Dockerfile.test` собирается из кэша и сам обновляется после выкатки.
  Отвергнуто: ставить pytest при каждом запуске (зависит от PyPI, версии плавают)
  и добавлять pytest в рабочий образ (лишнее в проде).
- Отдельный PostgreSQL, а не SQLite или рабочая база: запросы используют `jsonb`,
  `?|`, `ANY`, каскады — нужен настоящий PostgreSQL; рабочую базу трогать нельзя.
- Без настоящих запросов к LLM: бесплатно, быстро и детерминированно.
- Каждый набор проверен мутациями (поломка нужного места на копии кода роняет тест);
  мутации запускаются по одной — вместе они маскировали друг друга.
(`cac9c9e`, `c8adfa9`, `d25c7af`, `aa03256`)

## 2026-11-23 — Провайдер ModelRun исключён, обрезанный JSON спасается

**Проблема.** Ответ обрезался на лимите при маленькой группе: модель отдала корректный JSON,
а потом писала обычный текст по кругу до 8000 токенов. Провайдер — ModelRun.
**Решение.** `provider.ignore = LLM_IGNORE_PROVIDERS` (дефолт `ModelRun`) + `require_parameters`;
если ответ обрезан, но начинается с целого JSON, он используется.
**Почему.** Проверено запросами: одного `require_parameters` мало — ModelRun формально
заявляет поддержку JSON-режима и продолжает выбираться. Спасение JSON страхует от любого
провайдера с тем же поведением. (`reasderrss` `929e5a6`)

## 2026-11-23 — `other` только для погоды и разных событий

**Проблема.** Одиночные события (крушение лодки, фильм о члене королевской семьи) уходили в `other`.
**Решение.** В промпте: одно событие — подходящая категория; `other` — только погода или
«ничего не подходит», с двумя примерами. (`929e5a6`)

## 2026-11-22 — Справочник категорий на сервере, названия в `/meta`

**Решение.** `app/categories.py` — единый список: описания для промпта, какие принимаются,
русские названия. `/meta` отдаёт `category_titles`, клиент хранит их в DataStore и
показывает через `LocalCategoryTitles`; запасной словарь — для первого запуска без сети.
**Почему.** Новая категория — одна строка на сервере, без пересборки приложения.
(`reasderrss` `dab6801`, `d7856c5`; `newsreader` `622baa4`)

## 2026-11-22 — Спорт, культура, происшествия, светская хроника принимаются

**Проблема.** Эти темы отклонялись LLM, но запрос уже был оплачен — результат выбрасывался.
Фильтр по словам `SPORT_WORDS` вдобавок резал политику (`league` → Arab League, `match`).
**Решение.** Категории принимаются, скрываются в приложении; `SPORT_WORDS` больше не
исключает статьи (пометка `is_sport` осталась для статистики). Погода — по-прежнему `other`.
**Почему.** Дополнительный расход — в основном спорт, оценка $1–2 в месяц. (`a92bfc2`)

## 2026-11-22 — Потолок на размышления модели

**Проблема.** `qwen3.8-27b` иногда тратил все 8000 токенов на reasoning и не давал ответа
(диагностика: `reasoning_tokens=8000`, `content_chars=0`).
**Решение.** `reasoning.max_tokens = LLM_REASONING_MAX_TOKENS` (2000; 0 — выключить).
**Почему.** Проверены три варианта: `effort: low` — только пожелание, `enabled: false` —
модель перестаёт думать и хуже отбирает группы, жёсткий потолок — компромисс. Поднимать
общий лимит бесполезно: оплачиваются более длинные размышления. (`0f896ba`)

## 2026-11-22 — `MAX_ARTICLES` 200 → 1000 → 1500 (2026-11-23)

**Проблема.** За 36 ч набиралось ~600 статей, а в группировку шли только 200 самых свежих:
окно `lookback_hours = 36` фактически было ~11 ч. С 18 лентами — 1000+ статей.
**Почему не страшно.** Лимит стоит только CPU (эмбеддинги); LLM вызывается лишь для групп
из `min_sources`+ источников. (`383365d`, `929e5a6`)

## 2026-11-22 — Срок хранения данных и очистка

**Решение.** `retention_days` (дефолт 20, минимум 3) в `settings`; очистка — в конце
каждого успешного прогона; клиент чистит Room по тому же сроку из `/meta`.
**Почему.** Минимум 3 дня: иначе статьи, ещё лежащие в RSS, загрузились бы как новые.
Ручной `VACUUM` не нужен — autovacuum переиспользует место; `VACUUM FULL` блокирует
таблицы, только вручную. Клиент чистит сам, потому что тянет только новое по `since_id`.
(`f243830`, `df01a32`; `newsreader` `1432d17`)

## 2026-11-22 — Прогон, где все группы упали, — `failed`; повтор не чаще раза в час

**Проблема.** Со 2 по 20 ноября модель не отвечала, а прогоны получали `success` и
сдвигали шестичасовой интервал — сюжеты не создавались три недели незаметно.
**Решение.** Все группы с ошибкой → `failed`; интервал считается от последнего успешного;
повтор после неудачи — не раньше чем через `FAILED_RETRY_MINUTES` (60).
**Почему ограничение.** Без него стабильная ошибка (кривой JSON) давала бы 72 платных
попытки в сутки. (`e720313`)

## 2026-11-22 — Плашка «сервер давно не обновлялся» в ленте

**Проблема.** Кэш приложения маскирует отказ сервера: лента выглядит живой.
**Решение.** Клиент сохраняет `last_run_at` из `/meta`; если успешного прогона не было
дольше 12 ч (два интервала) — плашка над лентой; работает и офлайн. (`newsreader` `28af17f`)

## 2026-11-22 — Глубина ленты — фильтр показа, а не удаление

**Решение.** «Глубина ленты» (1/2/3/7 дн, все; по умолчанию 2) — фильтр в `FeedViewModel`.
**Почему.** Мгновенно и обратимо; удаление данных — отдельный механизм (`retention_days`).
Выбраны дни, а не число сюжетов: «за 2 дня» значит одно и то же при любой насыщенности.
(`newsreader` `1432d17`)

## 2026-11-22 — Адрес сервера в Gradle, а не поле в настройках

**Решение.** `BuildConfig.BASE_URL` в `app/build.gradle.kts`.
**Почему.** Сервер один. Поле в настройках потребовало бы перехватчика OkHttp и очистки
Room при смене сервера (иначе `since_id` и сюжеты двух серверов перемешаются) — сделаем,
только если понадобится переключаться на телефоне. (`newsreader` `ddb528f`)

## 2026-11-22 — Время последнего синка в DataStore

**Решение.** `lastSyncAt` пишется в `NewsRepository.sync()` — учитывает и фоновый
`SyncWorker`, переживает перезапуск. (`newsreader` `cd5c869`)

## 2026-11-19 — Причина «застывшего» воркера и команда выкатки

**Проблема.** Воркер с 4 октября работал на старом образе: сервис `worker` в профиле
Compose, `up --build` его не пересобирает. Старый код игнорировал `settings` и ходил в LLM
каждые 20 мин.
**Решение.** Выкатка: `docker compose up -d --build && docker compose build worker`.
**Почему не `--profile worker up`.** Он ещё и запускает прогон, который может пойти
параллельно с тиком таймера. (`0928708`)

## 2026-11-19 — `max_tokens` в запросе к LLM

**Проблема.** Без `max_tokens` OpenRouter резервирует под ответ весь контекст модели
(~131k токенов) и отвечает 402 при небольшом балансе.
**Решение.** `LLM_MAX_TOKENS` (дефолт 4000, на проде 8000). Платится только реально
сгенерированное. (`f1c226f`)

## Ранние решения (до 2026-11-18)

- **Сервер думает, клиент читает.** Дорогая работа (группировка, LLM) — один раз на
  сервере; клиент тянет готовые сюжеты инкрементально по `since_id` и работает офлайн.
- **Параметры пайплайна в таблице `settings`**, а не в `.env`: меняются без редеплоя,
  из админки.
- **Flavors `public` / `admin`** вместо скрытого раздела по паролю: публичная сборка
  физически не содержит админского входа.
- **Хранятся скрытые категории и источники, а не выбранные**: новое на сервере видно
  по умолчанию.
- **Две копии на сервере**: `~/reasderrss` — разработка, `/opt/reasderrss` — прод,
  обновляется только `git pull`; недоделанное не попадает в прод.
